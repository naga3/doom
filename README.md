# チェックボックスで描く DOOM

1ドット = `<input type="checkbox">` 1個。チェックの有無が白黒のピクセルで、
`transform: scale()` で1個の大きさを変えると 1bit より細かい濃淡も出せる、という表示装置の上に
Wolf3D 方式のレイキャスタを載せたものです。canvas も WebGL も使っていません。

同じシーンを `<table>` の `td` に描く表示方式も選べます。どちらが速いかは下の実測にあります。

- `index.html` — 歩けるデモ。表示方式・解像度・モードを切り替えて見比べられます
- `bench.html` — 描画コストの計測ページ

## 動かす

```sh
npm start        # http://localhost:4174
```

WASD で移動、左右キーかマウス（画面クリックでポインタロック）で旋回。

## 3つのモード

壁の高さはレイキャスタが小数で返します。それをドットの格子にどう落とすかが違います。

| モード | 壁の内側 | 壁の輪郭 | 見た目 |
|---|---|---|---|
| **A** | ベタ塗り | 行に四捨五入 | カリカリのドット絵。歩くと輪郭が1マス単位で跳ねる |
| **B** | ベタ塗り | 端数ぶん `scale()` で縮める | 輪郭だけが滑らかに動く。内側は A と同じ |
| **C** | 全セルの大きさで明暗 | 同じ | 網点（ハーフトーン）。新聞写真の質感 |

明暗は A / B ではベイヤー 4x4 の順序ディザ、C では大きさそのもので表します。

## 実測

```sh
node bench/measure.cjs 90
```

WSL2 + Chromium、実画面（ヘッドレスではない）、90フレーム。fps は同じ条件でも 1割ほど振れます。

| 解像度 | セル数 | A (checkbox / table) | B (checkbox / table) | C (checkbox / table) |
|---|---|---|---|---|
| 64 x 40 | 2,560 | 60.0 / 60.0 | 60.0 / 60.0 | 60.0 / 60.0 |
| 96 x 60 | 5,760 | 59.9 / 60.0 | 58.0 / 59.6 | 33.7 / **47.3** |
| 128 x 80 | 10,240 | 58.7 / 59.9 | 39.0 / **43.8** | 17.8 / **24.7** |
| 160 x 100 | 16,000 | 50.7 / 52.1 | 27.7 / 25.3 | 10.7 / **16.0** |

### 分かったこと

**1. 点けたり消したりは安い。大きさを変えるのは高い。**
A は 10,240 セルでも 60fps に届きます。一方 B は、1フレームの書き込みが 250個ほど増えるだけで
128x80 の fps が 3分の2 に落ちます。1書き込みあたり数十マイクロ秒という勘定で、しかも
この単価は格子が大きいほど上がります。1個書き換えるたびに格子全体を巻き込む再計算が
起きていると考えられます。

**2. 高いのは「書いた値」ではなく「書いたこと」。**
大きさの量子化段数を 1 / 2 / 4 / 16 段に変えても、B の fps はほぼ動きません
（128x80 で 42.5 / 43.5 / 43.2 / 42.7）。段数1はスケール指定が実質なくなる設定なので、
ネイティブ部品を新しい寸法で描き直すコストではない、と言えます。
（C の段数スイープは、段数を減らすとドット自体も消えて描画量が変わるため、この切り分けには使えません）

**3. `table` の `td` のほうが速い。**
A では差が出ませんが、大きさを変えるモードでは table が明確に勝ちます
（96x60 の C で 33.7 → 47.3 fps）。ネイティブのチェックボックスは、寸法が変わったときの
描き直しが素の `<i>` より重いということです。見た目をチェックボックスに寄せたいなら
その分の代金を払うことになります。

**4. JS の実行時間は問題ではない。**
`render ms` + `flush ms` は最悪でも 2.3ms しかありません。時間はブラウザの style 再計算と
再描画に出ていて、`performance.now()` では捕まりません。判断に使えるのは fps だけです。

### 解像度の決め方

- **A なら 128 x 80**（約 59 fps）。解像度を取るならこれ
- **B なら checkbox で 96 x 60、table なら 128 x 80**。輪郭の滑らかさを取るならこれ
- **C は table で 96 x 60**（47 fps）。網点は解像度を1段以上犠牲にする

解像度と輪郭の滑らかさはトレードします。B が A に対してほぼ無料になる、という当初の見込みは外れました。

### 未検証

インラインスタイルではなく、あらかじめ用意した CSS クラス（`.c0`〜`.c16`）の付け替えで
大きさを変えたらコストが変わるかは、まだ試していません。これが効けば B の値段は下がります。

## 構成

| ファイル | 役割 |
|---|---|
| `src/display.js` | 表示装置の共通部分。フレームバッファと差分の取り方 |
| `src/grid.js` | チェックボックス版の表示面 |
| `src/table-grid.js` | `<table>` 版の表示面 |
| `src/raycast.js` | マップと DDA レイキャスト |
| `src/scene.js` | レイキャスト結果を 1bit のフレームバッファに落とす。モードの違いはここだけ |
| `src/camera.js` | カメラ、当たり判定、計測用の自動歩行 |
| `src/engine.js` | 上をまとめた実行系。デモと計測で共有 |
| `src/main.js` | デモの入力とループ |
| `src/bench.js` | 計測ページ。`window.__bench` を公開 |
| `bench/measure.cjs` | Playwright で Chromium を回して表を出す |

### 格子を速く保つための約束

- 要素は起動時に1回だけ作る。以降は差分のあるセルだけ触る
- 消えているセルは `visibility: hidden`。未チェックの枠線が見えると黒が濁る
- 格子全体は1枚の `transform: scale()` で縮める。セルごとに `width` を変えると格子が崩れる
- `table` 版は `td` ではなく中の `<i>` を点滅させる。テーブルのレイアウトを触らない
- 格子には `aria-hidden` と `tabIndex = -1`。1万個のタブ停止点とクリックによる画面の破壊を防ぐ
